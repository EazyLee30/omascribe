## 执行规则

- 立即停止围绕三例事实原型持续调参。原型保持 `cfg(test)`，结果作为研究材料；本发布周期的修复必须进入实际生产链路并验证生产复现。
- 开发期间只跑受影响回归和必要源码检查。候选冻结后再跑完整语料、真实录音、原生窗口及安装升级流程；已冻结的失败版本和原始证据保留。
- 已签名CUDA/Vulkan组件继续复用，不做日常SDK矩阵重建、重签或反复编译安装包。源码修复及时推送。
- 分工固定：主线程修共享转写/纪要生产链路和Mac Metal适配；Windows修已报告的输入设备、停止和冷ASR问题；Linux / Omarchy只补本端启动、录音、系统音频和升级阻塞。共享输入契约变化提前在PR给出最小差异，避免并行改同一模块。
- 每次交付只报问题ID、提交SHA、受影响检查结果和剩余阻塞；小修通过即可提PR，不等待所有研究或所有平台事项完成。
- 两端各自报告当前head和必要阻塞项；主线程负责集成、候选SHA和发布范围。候选冻结后不新增功能、不滚动扩大研究门槛。
- 清单只更新失败复现、修复、验收结果或必要用户动作；不重复播报无变化的head/CI。报告须绑定候选SHA，不以不同版本的零散通过拼成验收通过。
- 在候选下一轮完整回归完成后再估算发布时间。0.3.5发布不等于整个优化目标完成，未完成研究继续独立推进。
