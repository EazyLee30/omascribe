## Apple Silicon priority

The shipped M-series runtime declares Metal enabled at llama.cpp revision `5aeac37a35b44fde4bdffaec9159f2fcb253b622`; its native `--list-devices` exposes `MTL0: Apple M5`. A real isolated fictional Chinese fact case passed on CPU and Metal. Explicit diagnostic verbosity 4 exposed **29/29 layers offloaded**, the MTL0 model/KV/compute buffers and shared buffers enabled. Default verbosity 3 hides those lines, so the initial diagnostic correctly did not accept configuration alone as proof. Raw local evidence: `artifacts/benchmarks/apple-metal-load-evidence-20261026/offload-summary.json`. The single case establishes execution, not a general quality/resource or speed result.

The same pinned 1.7B model and 18-case minutes corpus now pass twice per CPU/Metal backend, with reversed order and all repairs/failures counted. [Evidence](../evaluation/apple-metal-2026-10-27.json) records Metal 32.2/32.3 s and CPU 244.0 s plus a separate 247.7 s repeat; the contended first CPU arm is excluded from performance use. Runtime/CLI/model/source hashes and per-command offload proofs are bound to the result. Prefill/decode and sampled process resources are separate; case time includes loading but separate startup remains unmeasured. Translation-specific quality, integrated Windows 19-case source, sustained recording contention and older M-series still need tests. Runtime-reported Metal working-set/free figures must not be called independent physical VRAM or whole-system free memory. GPU allocation/energy values stay unknown unless measured by the worker or a suitable device API. Do not sum shared memory twice.

Two reversed-order 78-second Engine replay pairs now test ASR alone versus ASR plus Metal translation/minutes. The first measurement exposed timing-dependent ASR text despite equal PCM; fixed 200 ms decoder/leveling blocks pass both pairs with exact PCM/text, live translation/minutes progress and actual offload. Loaded p95 processing lag is 424 ms, with total sampled tree RSS around 1,681 MiB. The public two-model ASR corpus remains 24/24 with identical hypotheses. [Evidence and limits](../evaluation/apple-recording-2026-10-27.json) retain the original failure, post-change buffering tradeoff, pending end-of-recording minutes and unmeasured GPU physical allocation/energy.

Physical capture/long-meeting contention, real memory pressure/device faults and older M-series still need acceptance beyond these short replay/lifecycle tests. M5 measurements cannot establish M1/M2/M3/M4 performance; keep architecture/build compatibility and missing-device evidence visible. Compare targeted settings such as batching/attention only after an untuned production baseline, preserving facts/language/citations and the recording priority. MLX/CoreML remain separately gated experiments; CUDA/HIP/Vulkan SDKs stay outside base installers.

`536a842` adds Metal-specific actual-offload admission, one CPU retry after eligible runtime failures and a bounded model/runtime/config/meeting/run failure scope (persisted recording-take scope corrected in the follow-up below).
