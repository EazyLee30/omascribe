# OmaScribe website

Production: https://omascribe.eazylee.si/ — Cloudflare Worker `omascribe-site`, existing custom domain. Static HTML generated by Node.js; no application backend, analytics, external fonts or third-party browser scripts. `Cache-Control: public, no-transform` prevents Cloudflare automatic beacon injection; strict CSP also excludes external scripts. See [Cloudflare Web Analytics setup](https://developers.cloudflare.com/web-analytics/get-started/).

## Pages and data

Five separate pages: `/`, `/download/`, `/models/`, `/community/`, `/privacy/`. English equivalents use `/en/`; Traditional Chinese uses `/zh-TW/`. All 15 routes are built with canonical and alternate links, a sitemap and a real 404 page.

- `../model-catalog.json` supplies model names, sizes, licenses and supported model IDs. `src/copy.mjs` and `scripts/build.mjs` contain the three localized page versions.
- `../docs/benchmarks/*.json` supplies measured results. Summaries are checked against raw runs; no measurements means explicitly unmeasured. RSS is not unified GPU memory or whole-machine power. Conditions and raw results remain downloadable.
- `../community/profiles/*.json` is the reviewed gallery. Official suggestions and community submissions retain separate attribution. `../community/submissions/` is validated but excluded from the public gallery until a maintainer reviews and moves a file.
- `../community/profile-schema.mjs` validates both at build time and in the browser. Unknown fields, network permissions, arbitrary model URLs, commands and private paths are unsupported. Only known model IDs and bounded parameters are accepted.
- Gallery files are read in the browser, previewed, and exported as a submission file. The user uploads it on GitHub and opens a PR themselves; the website does not submit or publish it. App links are limited to 16 KiB, with a 64 KiB JSON-file fallback. Opening a link requests a desktop preview; it does not apply settings or download models automatically.
- `data/releases.json` is the latest verified metadata snapshot. `npm run sync:release` queries the official GitHub Releases API and selects the newest published release (including prereleases) containing all three platform installers and `SHA256SUMS.txt`. It validates exact repository asset URLs, nonzero sizes and upload completion; a failed refresh leaves the snapshot unchanged and exits unsuccessfully.
- `public/assets/brands/NOTICE.md` records upstream logo sources, hashes and software licenses. All assets are hosted on this origin.

The released v0.2.0 installers predate the new configuration and acceleration work. Pages state this explicitly; a new website deployment does not update an installed desktop application.

## Local commands

```sh
cd landing
npm ci
npm run sync:release  # network; optional GITHUB_TOKEN for API rate limits
npm run check        # build, boundary/data tests, syntax and Wrangler dry run
npm run dev          # http://localhost:8787
npm run deploy       # deploy existing Worker using authorized Wrangler credentials
```

`dist/` is generated and ignored. The build copies only required static assets and the shared schema. Website builds do not run or contact local inference. Local checks do not require a deployment token.

## GitHub deployment setup

The workflows are code-ready, but **automatic deployment is not active until they are committed/pushed and a dedicated credential is configured**. The local OAuth session must not be copied into GitHub.

1. In Cloudflare, create a scoped API token for the existing account `e4548d8e3c1446f8ed5f7d4cc8cfb318` and Worker deployment: Account → Workers Scripts → Edit. For the configured custom-domain route also allow Zone → Workers Routes → Edit and Zone → Zone → Read, scoped to the `eazylee.si` zone. Follow Cloudflare's current Workers deployment-token documentation; do not grant unrelated account access.
2. Add that token as repository Actions secret `CLOUDFLARE_API_TOKEN`. The non-secret account ID and existing route are in `wrangler.jsonc`.
3. Commit/push this directory, `community/`, the root model catalog, benchmarks and `.github/workflows/site*.yml`. If using an older `gh` OAuth credential, pushing workflow changes may require adding its `workflow` scope (or use an appropriately scoped SSH/PAT credential).
4. Run **Website deployment** once from GitHub Actions to verify. The job fails clearly without the secret; it does not silently claim deployment success.

`Website validation` checks affected PRs and main changes without deployment credentials. `Website deployment` deploys reviewed **main** on relevant pushes, a published release, manual dispatch, or a successful main-branch **Native release** workflow. The `workflow_run` trigger is necessary because releases published using `GITHUB_TOKEN` do not trigger other release workflows. It does not consume build artifacts or execute code from a PR. Deployment refreshes release data, validates, and then atomically uploads static assets to the existing Worker. No new paid resources are required.

An alternative is connecting the existing Worker to GitHub through Cloudflare Workers Builds (Settings → Builds), with `cd landing && npm ci && npm run sync:release && npm run check` and deployment command `cd landing && npx wrangler deploy`. That Git connection requires account authorization and does not alone refresh on releases; the included GitHub workflow covers both code and release events.
